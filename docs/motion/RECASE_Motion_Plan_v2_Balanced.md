# RE:CASE — Motion Plan v2.0 (Balanced)

**Статус:** согласован уровень насыщенности Balanced; спецификация для предварительного аудита ассетов и последующей реализации.  
**База:** `recase all screens.pdf`: с. 1 Desktop, с. 2 Tablet 744, с. 3 Mobile 390.  
**Важное ограничение:** PDF — источник композиции, но не подтверждает, как графика разбита на DOM-слои в текущем коде. Конечный сайт и его текущие ассеты ещё нужно проверить.  
**Концепция:** **Pixel Motion / Retro Digital** — сайт ощущается как оживший интерфейс ретрокомпьютера, но остаётся читаемым, быстрым и функциональным.

## 1. Набор эффектов — статус v2

Обозначения: **Core** — главный фирменный эффект; **Standard** — единая малозаметная механика; **Conditional** — только при наличии нужных графических слоёв; **Keep** — сохраняем существующее поведение; **Drop** — сознательно не реализуем.

## 2. Технологический выбор

| Технология | Применение | Решение |
|---|---|---|
| CSS transitions / keyframes (`steps`, `opacity`, `transform`) | Hero headline, небольшие snap/fade, UI-реакции | **Используем** |
| `IntersectionObserver` | Запуск при входе в viewport, один раз, общая система scroll reveal | **Используем** |
| Web Animations API / `Element.animate()` | Координация небольших вступительных последовательностей при необходимости | **Используем точечно** |
| `requestAnimationFrame` + позиционированные DOM-particles | 6–12 отдельных пикселей, desktop mouse proximity | **Используем, если ассеты позволяют** |
| Canvas 2D | Сотни частиц, сложная физика | **Не нужен в Balanced** |
| GSAP + ScrollTrigger | Сложный scrubbed-scroll, pinning, насыщенные timelines | **Не устанавливаем сейчас**; возможен лишь после подтверждённой необходимости |
| Motion (`motion/mini`) | Дополнительная компактная библиотека для декларативного движения | **Не нужен сейчас**, нативный стек закрывает задачи |
| Three.js / shaders | 3D и тяжёлые графические эффекты | **Исключаем** |

**Рекомендация:** начать с **нулём новых runtime-зависимостей**. Если при реализации M08/M13 обнаружится действительно сложная координация, пересмотреть решение по GSAP на основании прототипа, а не устанавливать заранее.

Названия ниже присутствовали в раннем `assets.json` проекта, **но актуальная GitHub-кодовая база пока не проверена**.

| Сцена | Вероятный текущий ассет | Что проверить | Если всё объединено в картинку |
|---|---|---|---|

| Hero — заголовок и форма | `hero-pixel-underlay.png`, `hero-texture.png` | Не является ли текст частью растра? Не возникнут ли seams при reveal? | Раскрывать единую композицию через маску, не дробить форму |

| Стикеры | `idea-sticker.svg`, `team-sticker.svg` | Самостоятельные ли элементы и корректен ли transform-origin? | Их можно анимировать отдельно без новых ассетов, если уже отдельные DOM-узлы |
| Roadmap | набор существующих border SVG и HTML карточек | Карточки — отдельные DOM-элементы; SVG не растягиваются? | Анимировать контейнеры целиком, геометрию SVG не трогать |
| Пиксельные маски секций | `format-mask.svg`, `audience-mask.svg` и др. | Сохраняются ли швы при transform/opacity? | Оставить маску неподвижной, двигать только внутреннее содержимое |

**Приоритет экспорта, если нужен:**
1. Отдельные прозрачные слои иллюстрации «Проблема»: персонаж, двери, X, компьютер.
2. Отдельный экран/световой слой Hero-компьютера — **только если хотим настоящий boot-effect**.
3. Отдельный экран/стикеры «Формат» — только если хотим сюжет загрузки файла.
4. Отдельные частицы — только если текущие декоративные квадраты слиты с изображениями и их нельзя легко выделить.

Пробовать экспортировать из Figma через MCP в lossless PNG/WebP (для многослойных пиксельных картинок) или SVG (только для чистой геометрии без seams). Не извлекать слои обратно из плоских PNG алгоритмически без причины.

## 4. Motion tokens — стартовые рамки

- UI hover/focus: 100–180 мс, active 70–110 мс (уже реализованы — не перезаписывать).
- Появление карточки: 240–380 мс, `translateY(6–10px)` + `opacity`; spacing в DOM не меняется.
- Stagger: 80–130 мс между соседними элементами.
- Пиксельное раскрытие: 450–600 мс, `steps(6–10, end)`; тестировать без полос/швов.
- Boot sequence компьютера: 450–650 мс, после/во время окончания заголовка.
- Двери: общая история <= 1,2 с, без блокирования scroll/CTA.
- Roadmap: 300–450 мс на карточку, каждая запускается при видимости.
- Курсорные частицы: реакция до ~200 мс, возвращение ~350–500 мс; desktop only.

Это ориентиры до прототипирования, не требования анимировать каждый элемент.

## 5. Правила доступности и производительности

- `prefers-reduced-motion: reduce`: декоративное движение полностью отключается, контент виден сразу.
- Hover и курсорная реакция только при `hover: hover` и `pointer: fine`.
- Сайт и формы работают без JavaScript-анимаций; не ставить `opacity: 0` на контент по умолчанию в HTML/CSS до инициализации.
- Если сцена ниже viewport, анимация стартует только при попадании в видимую область; observer отключается после первого запуска.
- Анимировать преимущественно `transform`/`opacity`, а не `width`, `height`, `top/left` для больших элементов; avoid layout shifts.
- Не дублировать существующие hover/active, модальные окна и mobile-menu transitions.
- Не изменять пиксельные края, clip-path крупных розовых/лаймовых секций, пропорции SVG-рамок и responsive layout.
- Избегать внешних CDN и новых внешних runtime-запросов.

## 6. План реализации и критерии

### Phase 0 — Read-only audit (следующий шаг)
Определить текущий DOM, source assets, структуру CSS и существующие анимации/hover. Выдать таблицу готовности M01, M02, M03, M08, M10, M13: `ready / need-layer-export / risky` с файлами и краткой стратегией. **Код не менять**.

### Phase 1 — Hero prototype
M01 + M02 с graceful fallback, на Desktop/Tablet/Mobile. Проверка: 1512x900, 744x1024, 390x844; кнопки доступны, без CLS/seams. Один разумный цикл визуальных корректировок при необходимости.

### Phase 2 — Desktop particles
M03 только при `pointer: fine`, без конфликтов с Hero/CTA, выключено в reduced-motion. Проверить движение указателя и отсутствие просадок на ноутбуке.

### Phase 3 — Narrative motion
M08 (если подготовлены слои) и M13. Проверить фактическую последовательность при скролле, без повторного проигрывания и деформации рамок.

### Phase 4 — Reusable scroll reveal
Один переиспользуемый механизм для M05/M07/M09/M11/M15/M16/M17/M18. M10 и M14 — только если есть отдельные слои и визуальная польза. M19 оставить как есть.

### Phase 5 — Motion QA
Целевая проверка Desktop/Tablet/Mobile, reduced-motion, клавиатуры, якорей, меню, модалок и работы без JS-motion, затем `npm run build`; устранить только реальные дефекты.

- Можно ли разделить `selection.png` на слои через существующий Figma MCP.
- Как представлены particles: отдельные DOM/SVG или впечены в PNG/маску.
- Есть ли самостоятельные карточки Roadmap и стабильные селекторы.
- Какие эффекты можно сделать нативно без зависимостей.
- Какие ассеты нужно предоставить вручную / экспортировать из Figma.
- Предлагаемые небольшие CSS/JS модули для реализации **без изменения кода на Phase 0**.
