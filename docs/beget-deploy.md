Актуальная архитектура, 14 октября 2026: статический Vite frontend на Layero
Free → `https://matveyyb.beget.tech/api/lead.php` → существующая MySQL
`matveyyb_recase` → существующий `@recase_appl_bot`, закрытая группа
`-5275551751`. Эта подготовка не выполняет деплой, push или реальные отправки.
База и бот уже созданы владельцем; миграция v1 уже успешно применена.
**Не создавать новую базу/бота и не применять SQL повторно.**

Frontend публикуется независимо: [Layero](layero-deploy.md).
Production-адрес ещё не подтверждён; желаемый `recase.layero.app` не записан
в серверный allowlist. `re-layero-free-smoke` — только диагностика.

## Поведение

Layero frontend → `POST https://matveyyb.beget.tech/api/lead.php` → PDO / MySQL виртуального хостинга Beget →
HTTPS Telegram Bot API. Дизайн и утверждённые попапы сохраняются. Благодарность
с исходным текстом показывается по прежнему контракту: HTTP 200, `ok: true`,
`status: accepted`. Теперь он означает **подтверждённое сохранение в MySQL**,
а не получение сообщения организатором. Ошибка базы возвращает общий JSON 503.

Уникальный UUID заявки — PRIMARY KEY на весь срок хранения, независимо от IP.
Изменённые данные с прежним UUID дают 409. Повтор с новым UUID считается новой
заявкой; защита не пытается запрещать человеку все дальнейшие регистрации.
Блокировка InnoDB строки HMAC(IP) обеспечивает атомарный скользящий лимит:
по умолчанию 5 новых валидных заявок за 10 минут. Повторы существующего UUID
не расходуют квоту. Учитывать общий IP университета. Это не защита от DDoS
или ботнета; HTTP/Origin сами по себе не аутентификация пользователя.

Сохранение заявки, consent/version, срока, задания уведомления и события лимита
происходит одной транзакцией. Telegram вызывается только после COMMIT.
Повторные запросы посетителя не инициируют ещё одну отправку.

с поддержкой TLS, штатные JSON/filter/hash/ctype/PCRE; OpenSSL проверяется
bootstrap. [PHP-расширения Beget](https://beget.com/ru/kb/how-to/web-apps/php).
Путь CLI PHP уточнить в панели/поддержке, не полагаться на системный `php`:
`php -v` должен показывать 8.3+. Публичный phpinfo не выкладывать.

## Секретная конфигурация

Только на сервере, в приватном каталоге:
```sh
umask 077
cp config.example.php config.php
chmod 600 config.php
```

Редактировать серверный файл приватным редактором/SFTP, без вывода его содержимого
в общий терминальный журнал. Не передавать токен в URL браузера, аргументах
команды, JS, Git или чате с ассистентом. Токен и chat_id не входят в пакет.

Заполнить `mysql.database`, `username`, `password` из панели; `host: localhost`.
`unix_socket` для production оставить пустым, если Beget не указал иной параметр.
Сгенерировать стабильный `rate_secret` командой
`php -r 'echo bin2hex(random_bytes(32));'` в приватной сессии и записать в config.
Смена секрета меняет HMAC/fingerprint и квоты; не менять его произвольно в период
приёма. После вынужденной смены прежние UUID могут давать 409.

`consent_version` — версия **действительно утверждённого опубликованного**
согласия; сохранить его отдельную неизменяемую копию для подтверждения версии.
Поле намеренно пустое в примере, пока документ не согласован. Версия записывается
при первом сохранении; повтор не изменяет её. Старый экран согласия из другого
релиза нельзя считать доказательством принятия новой редакции: на смену документа
нужен отдельный порядок обновления открытых форм/версий, без тихой подмены.

`site_origin` — **точный подтверждённый production-origin Layero** без slash,
пути, userinfo, query или fragment. В примере пусто: это намеренный fail closed.
Скопировать адрес из результата Layero, а не из желаемого имени. Должен совпадать
с `VITE_SITE_ORIGIN` frontend. Beget-origin, Pages и smoke в allowlist не добавлять.

CORS: точное сравнение Origin, только HTTPS; `Vary: Origin` на всех ответах.
Для разрешённого origin выставляются `Access-Control-Allow-Origin` (ровно он),
`Access-Control-Allow-Methods: POST`, `Access-Control-Allow-Headers: Content-Type`.
OPTIONS с requested method POST и допустимыми headers получает 204 без тела,
MySQL и Telegram; работает и при выключенном intake. Неподходящий origin,
отсутствующий Origin, HTTP, запрос иных preflight headers/methods → 403.
Ошибка API для разрешённого origin тоже доступна браузеру через CORS.
Неверная/пустая серверная конфигурация → 503 без разрешающего origin.
Cross-site Fetch Metadata допускается только после точного совпадения origin.
Credentials/cookies не используются, wildcard отсутствует. CORS не аутентификация:
небраузерный клиент может подделать Origin. Валидация, квоты и UUID остаются.

Не добавлять параллельные Access-Control-* заголовки в панели/Apache/CDN.
API не должен перенаправлять POST: frontend отклоняет redirects.
Дата завершения: `2026-11-15T23:59:59+02:00`, год 2026 принят по текущему событию.
Срок хранения — календарный месяц, до конца `2026-12-15` в UTC+2.
Срок фиксируется в каждой заявке; изменение даты не продлевает старые записи.
Более ранний общий срок блокирует отправку и очищает старые записи.

По **новому прямому указанию владельца** в примере уже выбраны
`telegram.enabled: true` и `personal_data_enabled: true`. Полный plain-text:
тип, имя, контакт, время UTC. Это целевая настройка, а не доказательство правовой
готовности. `enabled: false` верхнего уровня сохраняется до настройки и запуска.
Для обезличенного режима есть `personal_data_enabled: false`.
У уже обезличенной очереди персональные данные впоследствии не добавляются;
выключение полного режима действует и на ещё не отправленные полные заявки.

## Доставка, повторы и наблюдение

- `pending` — сохранено, отправка ещё не началась.
- `sending` — атомарно захвачено одним обработчиком, lease/token записаны до сети.
- `sent` — подтверждён HTTP 200 / Bot API ok=true / message_id.
  Это принятие Telegram, не подтверждение прочтения организатором.
- `failed` — доказанная ошибка до передачи либо подтверждённый отказ Bot API
  400/401/403/404/429. Можно повторить с задержкой, максимум 5 попыток.
  При 429 соблюдается retry_after; обычный backoff от 60 секунд.
- `uncertain` — timeout, обрыв после возможной передачи, 5xx, невалидный ответ,
  либо прерванный `sending` старше 10 минут. **Автоповтор запрещён**.

Если Telegram подтвердил сообщение, а запись квитанции в БД сорвалась,
`sending` остаётся заблокированным и затем становится uncertain.
Bot API не предоставляет ключ дедупликации sendMessage: абсолютная exactly-once
доставка между MySQL и Telegram не обещается. При неопределённости надёжнее
оставить заявку в БД и проверить вручную, чем автоматически размножать сообщения.

`php status.php` показывает только счётчики состояний и исчерпанных попыток.
Имена/контакты просматриваются только уполномоченным организатором через приватный
доступ к БД (например, phpMyAdmin панели), не через открытый web endpoint.
Скрипт повтора не требует верхнего `enabled: true`: выключение приёма не блокирует
доставку ранее сохранённой очереди. Для остановки отправки задать отдельно
`telegram.enabled: false`.

После расследования uncertain:
```sh
php resolve-notification.php <UUID> sent --confirm
# либо ТОЛЬКО при подтверждённом отсутствии отправки:
php resolve-notification.php <UUID> not-sent --confirm
```

Команда сама не отправляет сообщение. not-sent допускает дальнейшую обработку
cron, сохраняя общий предел попыток. Отсутствие сообщения в видимой истории чата
само по себе не доказывает, что его не отправляли. Если результат установить
нельзя, оставить uncertain; контакты остаются доступны в БД до удаления.

Для cron подставить проверенный **абсолютный** PHP 8.3+ и приватный путь:
```cron
* * * * * /path/to/php83 /home/<login>/<site>/private/recase-server/retry-notifications.php --limit=20
*/5 * * * * /path/to/php83 /home/<login>/<site>/private/recase-server/cleanup.php
```

Указать эти команды через CronTab в панели. Не перенаправлять вывод/ошибки
в public_html. CLI выводит только общие статусы/счётчики, не исключения и данные.
Одновременные workers безопасны благодаря атомарному claim; таймаут запроса
Telegram 8 секунд, connect timeout 3, TLS peer/hostname проверяются.
Встроенного мониторинга SLA нет: организатор проверяет status и ошибки cron;
исчерпанные/uncertain требуют ручного разбора.

## Удаление и резервные копии

Время хранится в UTC. После cutoff API и очередь не используют истёкшие данные.
`cleanup.php` физически DELETE-ит истёкшие записи и старое состояние лимитов.
При cron каждые 5 минут физическое удаление может запаздывать до 5 минут,
при неработающем cron — дольше. Для соблюдения предельного срока назначить
контрольную очистку **до его истечения**, проверить количество строк и результат.
Обработка, начавшаяся за несколько секунд до cutoff, может завершиться после
него; организационный останов отправок/очистку назначить заранее.

SQL DELETE не доказывает стирание резервных копий, binlog, временных экспортов
и остаточных страниц хранилища Beget. До запуска получить у Beget конкретный
срок хранения копий и возможность их удаления/ограничения доступа; согласовать
порядок уничтожения, а не считать обычный rolling backup исключением из срока.
Если провайдер не обеспечивает нужный режим, правовую готовность не считать
подтверждённой. Удалять свои дампы/экспорты, вести акт без данных заявителей.
Восстановление делать изолированно, с выключенными API и Telegram; сразу
выполнить cleanup с текущим сроком и проверить БД перед открытием доступа.

Telegram — отдельная копия персональных данных. Не обещать автоматическое
удаление ботом спустя месяц: [deleteMessage](https://core.telegram.org/bots/api#deletemessage)
обычно ограничен 48 часами. Нужен регламент ручного удаления для всех участников,
экспортов/скачиваний и устройств с подтверждением исполнения либо отдельно
проверенная политика auto-delete чата, согласованная до приёма.
protect_content уменьшает возможность пересылки/сохранения, но не устраняет
скриншоты и не гарантирует удаления всех копий. Удаление из MySQL не удаляет
Telegram; полный режим не включать организационно без выполнимого регламента.

## Правовые условия полного режима

Код уже поддерживает выбранный владельцем полный режим. До реальных заявок
оператор должен согласовать:

1. Политику и отдельное согласие под фактическую схему MySQL + Telegram,
   цели, состав данных, получателей, сроки, отзыв и уничтожение. Существующие
   юридические HTML здесь **не изменены**; прежнее описание PHP/SMTP недостаточно.
   [Статья 9 152-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_61801/6c94959bc017ac80140621762d2ac59f6006b08c/).
2. Локализацию первичной обработки на инфраструктуре РФ и меры безопасности
   Beget; российская MySQL не подтверждает хранение Telegram исключительно в РФ.
   [Статья 18](https://www.consultant.ru/document/cons_doc_LAW_61801/cbf4e15b7c330f9372e876cdf2bc928bad7950ef/).
3. Правовое основание передачи Telegram, применимость трансграничной передачи,
   иностранных получателей/стран и возможность получить требуемые сведения.
   Если передача трансграничная — отдельное предварительное уведомление
   Роскомнадзора, соблюдение сроков/решений и ограничений по
   [статье 12](https://www.consultant.ru/document/cons_doc_LAW_61801/e4ebbe1780de623c7cf32a59ca82a7bb523a25dd/).
   Закрытый чат и согласие пользователя сами по себе этих требований не заменяют.
4. Перечень организаторов, доступ, обязательства конфиденциальности, защита
   аккаунтов, отзыв доступа и регламент удаления БД/backup/Telegram.
   Если это нельзя обеспечить, использовать обезличенное уведомление и БД.

Это список вопросов для оператора и правового согласования, а не заключение
о законности конкретной передачи. Платные сервисы и DBaaS не подключались.

## Серверное тестирование и запуск — после разрешения на деплой

1. Разместить пакет, оставить верхний enabled=false. Выбрать PHP для сайта/cron,
   закрыть приватные каталоги, проверить сертификат и HTTP→HTTPS.
2. Подключить существующую `matveyyb_recase`, задать приватный config.
   Не импортировать v1 повторно и не запускать migrate.php.
   На сервере: `php check-runtime.php --db --network`. Это SELECT/проверка схемы
   и GET `https://api.telegram.org/` **без токена**, без отправки.
   HTTP 2xx–5xx с успешным TLS подтверждает только транспорт.
3. Проверить существующий частный chat_id через CLI выше. Настроить cron и status.
   Утвердить документы, версию согласия, удаления и доступы.
4. Только по разрешению включить intake и выполнить две синтетические заявки
   участника/партнёра: одна строка на UUID, правильное согласие/срок, sent,
   реальное получение в правильной группе, привычная благодарность.
5. Параллельно повторить неизменённый UUID: одна строка и одно сообщение.
   Проверить changed UUID payload→409, consent→422, Origin→403, лимит→429.
   Изменение данных с НОВЫМ UUID — новая заявка.
6. В согласованном тестовом окне отключить Telegram, сохранить заявку→pending,
   включить и выполнить worker. Ошибки БД/сетевого ответа моделировать только
   на локальной/изолированной тестовой БД, не ломать production.
7. По окончании синтетического окна снова выключить intake/frontend, пока нет
   отдельного разрешения на реальные заявки. До открытия реального приёма проверить оба PHP runtime, HTTPS, cron,
   резервные копии/удаление, недоступность private по HTTP и документы.

Публичный HTTPS целевого сайта 14 октября проверялся из локальной среды:
handshake завершился `SSL_ERROR_SYSCALL`, HTTP-ответ не получен. Это не доказательство
ошибки сертификата и не серверный тест Beget. PHP/расширения/исходящий Telegram
на Beget пока не подтверждены — нужны серверные проверки после размещения.

## Сохранённый SMTP вариант и локальные проверки

`app.php`, `mailer.php`, PHPMailer и прежние 72 теста сохранены.
`config.smtp-legacy.example.php` включает явный `backend: smtp_legacy`.
Старый config без backend остаётся совместимым. SMTP-ветка сохраняет прежнюю
семантику accepted и file-state; она не отправляет дополнительно к MySQL/TG.
Не переключать backend во время приёма без плана очереди и сохранения заявок.

```sh
npm run test:php
npm run test:cors
npm run test:mysql
npm run test:frontend
```

Браузерным тестам нужен установленный Playwright и Chromium/Chrome;
`RECASE_TEST_NODE_MODULES` задаёт путь к node_modules, `RECASE_TEST_BROWSER` —
путь к уже установленному браузеру. Все внешние запросы перехватываются.
Нужны локальные PHP 8.3+ с PDO MySQL/cURL/php-cgi и mysqld.
test:mysql запускает одноразовую socket-only MySQL без TCP и без production config,
после теста останавливает её и удаляет каталог. Никаких реальных Bot API вызовов.
На этом Mac:
```sh
RECASE_TEST_PHP=/opt/homebrew/opt/php@8.3/bin/php \
RECASE_TEST_MYSQLD=/opt/homebrew/opt/mysql@8.4/bin/mysqld npm run test:mysql
/opt/homebrew/opt/php@8.3/bin/php tests/lead-test.php
```

Список изменений и результаты — [docs/launch/README.md](launch/README.md).
