# RE — статический Vite frontend на Layero Free

**Актуальный production:** https://recase.layero.app/ — опубликован 14 октября 2026.
Рабочие заявки используют Яндекс Формы; Beget ниже — сохранённая резервная схема.
[Production QA и две тестовые заявки](launch/recase-production.md).

Для следующей разрешённой публикации: сборка `npm run build:layero` с публичными
переменными из `.env.layero.local`, затем запуск CLI **из папки `dist/`** с
`--project recase --yes --json`. Удалить только служебные `.gitkeep` из результата.
Не использовать `--root dist` из корня репозитория: он загружает весь рабочий каталог.
Публикуется только готовая статика, Node runtime не нужен.

## Проверка Free

Проверено по официальным источникам 14 октября 2026:

- [Free](https://docs.layero.ru/billing/plans/) допускает размещение на адресе
  платформы, до 5 проектов; индексация, свой домен и удаление плашки требуют Pro.
- [Vite](https://docs.layero.ru/getting-started/frameworks/) — статический пресет,
  результат `dist`. Node нужен только для сборки, runtime/startCommand не нужны.
- [Переменные](https://docs.layero.ru/deploys/env-vars/) доступны при сборке;
  `VITE_*` встраиваются в публичный JS. Менять URL/включение можно только
  новой сборкой. MySQL/Telegram секреты на Layero не задавать.

Технически утверждённая архитектура подходит Free. Проверку фактического плана,
свободного места среди проектов и имени выполнить перед согласованным деплоем.
Платные функции, Pro и карту не подключать. Плашку платформы не скрывать.

## Production-конфигурация

Скопировать `.env.layero.example` в игнорируемый `.env.layero.local` для локальной
сборки либо задать эти **публичные** переменные на Layero для стадии build:

| Переменная | Значение |
| --- | --- |
| `VITE_BASE_PATH` | `/` |
| `VITE_LEAD_API_URL` | `https://matveyyb.beget.tech/api/lead.php` |
| `VITE_SITE_ORIGIN` | подтверждённый HTTPS origin основного проекта без slash |
| `VITE_LEAD_API_ENABLED` | `false` до согласования и разрешённого E2E окна |

`npm run build:layero` создаёт три HTML и assets в `dist/`, без PHP/SQL/секретов.
Для сборки на платформе: framework **Vite**, команда `npm run build:layero`,
output `dist`, Node 24. Никакого Node runtime, порта, сервера или БД на Layero.
Обычный `npm run build` намеренно всегда выпускает preview без отправки,
даже при случайном `VITE_LEAD_API_ENABLED=true`.

## Публикация после разрешения

Для первого ручного выпуска удобно загрузить **только готовый `dist/`** как
статический сайт: это исключает загрузку backend и приватной конфигурации.
Выполнить `npx layero@latest deploy --dry-run --root dist --json`, проверить
static / отсутствие runtime и привязки к smoke. Только после разрешения
на публикацию выполнить CLI upload этой папки с желаемым именем `recase`.
Не использовать `--claim` или случайный дополнительный проект при конфликте
имени: согласовать другое имя. Не выполнять git push. Для будущего Git-flow
можно подключить существующий репозиторий отдельно по разрешению; build settings
указаны выше. В текущем этапе ни проект, ни переменные в облаке не меняются.

Первый выпуск держать с выключенным API. Из результата публикации взять точный
production origin, затем одинаково записать его в `VITE_SITE_ORIGIN` и приватный
Beget `site_origin`. Не разрешать preview/branch/Pages/smoke адреса.
Если build-команда платформы остаётся `npm run build`, формы останутся выключены.

## Проверка опубликованных файлов и форм

1. Проверить HTTPS, главную, `/privacy-policy.html`, `/personal-data-consent.html`,
   локальные шрифты/изображения и обе формы на desktop/mobile. Юридические ссылки
   должны открывать страницы frontend на Layero. Дизайн и motion не менять.
2. До разрешения E2E убедиться в Network, что отправка формы не вызывает API,
   показывает существующее сообщение недоступности, сохраняет введённое.
3. Проверить Beget по отдельной инструкции: HTTPS и OPTIONS, точный origin,
   CORS-заголовки на ошибках, MySQL/Telegram/cron/private.
4. После согласования обработки данных и отдельного разрешения на тестовое окно
   включить серверный `enabled` и frontend `VITE_LEAD_API_ENABLED=true`, пересобрать
   и выполнить две вымышленные заявки participant/partner. Проверить MySQL до
   Telegram, типы, согласие, срок, доставку в существующую группу и благодарность.
5. Неизменённый повтор UUID не создаёт строку/уведомление; ошибка соединения
   сохраняет данные. Успех — только `200`, `ok:true`, `status:accepted`.
6. Снова выключить intake и frontend после тестового окна до отдельного допуска
   реальных заявок. GitHub Pages проверить отдельно: никаких POST к Beget.

На localhost, `.github.io`, чужом origin и в dev/preview реальная отправка
блокируется. Frontend не использует cookies, хранилище браузера или credentials;
редирект API считается ошибкой. CORS не является защитой от произвольного клиента:
сервер сохраняет валидацию, HMAC rate limit и UUID/fingerprint дедупликацию.
